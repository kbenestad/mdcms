# Unreleased changes

Changes merged into `development` that have not yet been released to `main`.

---

- Running `mdcms` with no subcommand now clears the terminal and shows a status banner (wordmark, version, release date, and an up-to-date/outdated message fetched from `docs/banner/`) above the usual command list.
- Post listings (`posts-created-*` tags) now stack on narrow viewports (≤ 600px): date/time on one line, the title link underneath, with extra space below the link before the next item. Previously the fixed-width date column squeezed titles into a sliver and could overflow the viewport on phones.
- All `posts-created-*` tag variants were verified working end-to-end in-browser (both orders; `byyear`, `byyearmonth`, `lastyear`, `lastmonth` modifiers; `limit`, `paginate: yes/no/none`, year selector, post-link navigation). The "most variants are broken" warnings were removed from `CLAUDE.md` and `docs/reference-pages.md`, and the incorrect `paginate:` mode descriptions in `reference-pages.md` were corrected (`yes` = full page bar, `no` = "Load more", `none` = hard cap).
- `toc-section` now accepts its section id in all three natural spellings: `toc-section reference` (the only form that worked before), `toc-section: reference` (previously rendered "Unknown tag"), and a `section: reference` option line (previously silently ignored, falling back to the current page's section). Docs updated to show all three.
- `sample-sites/hearth-and-bean/index.html` was re-synced with the canonical renderer — it had missed earlier renderer syncs (no collapsible sidebar) because the re-sync checklist in `CLAUDE.md` still listed seven sites; the list now includes all eight.
- Theme files now carry their own version marker (`# mdcms theme v0.6.0`), replacing the stale, misleading `# mdcms v0.4 | DO NOT REMOVE THIS COMMENT` line across the whole theme library and the starter `theme.yml` (these landed straight on `main`, per the themes branching convention). `mdcms build` now checks the site's installed theme against `MIN_SUPPORTED_THEME_VERSION` (0.6.0) via `_ensure_theme_current()`: an unmarked or older library theme is automatically re-fetched from the theme library and written back to the path `config.yml`'s `theme:` key names; a non-library starter `theme.yml` is warned about instead. The check is non-fatal — any problem is a warning and the build still completes.
- New `mdcms bundle [name]` command builds a single self-contained `bundle.html` — config, theme, nav, search index, every page/post, and referenced assets embedded inline — so a site can be opened from any storage (USB stick, email attachment, wiki upload) with no server and no sibling files. Mechanism: a small shim patched into the bundled copy monkey-patches `window.fetch` to serve embedded content for the paths the renderer already fetches (config/theme/nav/search/pages/icons), plus a handful of literal source patches for call sites that build asset paths by string concatenation instead of `fetch()` (favicon, logo, category fonts). Also patches `navigateTo()`'s history calls to only run under `http:`/`https:` — the renderer's clean-URL routing otherwise throws a `SecurityError` when the address bar can't be rewritten to an on-disk path that isn't the opened file, whether that's a `file://` path on desktop or a `content://media/external/...` URL from opening the bundle via an Android file manager/browser "open with" (the initial `file:`-only guard missed this second case — fixed to allow-list real served origins instead of block-listing individual opaque schemes). `--offline` additionally downloads and inlines the CDN vendor JS/CSS libraries and any Bunny/Google web fonts, so the bundle needs zero network access ever; without it those still load from CDN when the file is opened. Bundle output never includes PWA install/service-worker references, regardless of the site's `pwa:` setting — a single file has no separate origin for a service worker to manage. `app/index.html` itself is untouched; this only affects the generated `bundle.html` copy.
- Fixed a renderer crash in any sandboxed context that lacks `allow-same-origin` (observed opening a bundle from OneDrive's in-browser HTML preview): merely touching `localStorage` throws a `SecurityError` there, not just returning an empty value, and several call sites (theme preference, sidebar-collapsed state, nav-section expand/collapse state, the offline-message cache) accessed it directly without a guard. All `localStorage` reads/writes now go through a new `safeStorage.get()`/`safeStorage.set()` helper in `app/index.html` that catches and no-ops — same fallback behaviour as the two call sites that already had an ad hoc try/catch. Re-synced into all eight sample sites per the usual renderer-sync checklist in `CLAUDE.md`.
- `docs/install.md` gained a "Building your own binary" section covering the PyInstaller command the release workflow uses (`pyinstaller --onefile --name mdcms --collect-data certifi mdcms.py`), the venv workaround for `externally-managed-environment` pip errors on modern Debian/Ubuntu, and how to run the resulting binary straight out of `dist/` without installing it (and how to check `which -a mdcms` if an existing install would otherwise shadow it).
- Fixed `mdcms bundle --offline` embedding literal control-byte characters (a raw BEL and ESC byte, from js-yaml's minified escape-sequence lookup table — perfectly valid inside its own JS string literal) verbatim into the output file. Some mobile file-preview sniffers (observed: NextCloud and OneDrive's mobile apps, "Stream contains non-printable characters") refuse to render an HTML file containing raw control bytes at all, even though the browser itself handles them fine. Vendor `<script>` content downloaded for inlining is now passed through `_bundle_escape_js_control_chars()`, which rewrites any raw control byte as its `\xNN` JS escape — semantically identical inside any JS string/regex literal, which is the only place such a byte can validly occur in already-valid JS source. Inlined vendor `<style>` content and web-font CSS get the equivalent `_bundle_strip_control_chars()` (CSS has no comparably safe short escape, and legitimate CSS shouldn't contain one anyway). Config/nav/search/page content was never affected — those go through `json.dumps()`, which already escapes control bytes.
